# Technical Memo: Simulation Validity and Data Interpretation Guidelines

This technical memo establishes the methodological framework for interpreting, citing, and analyzing the results generated by the HEXA-MoE co-design simulation infrastructure. Due to the hybrid nature of the evaluation (combining event-driven system-level simulation with cycle-accurate microarchitectural gem5 execution), different output metrics possess varying degrees of physical fidelity and abstraction.

---

## 1. Classification of Simulation Metrics by Fidelity

### 1.1 High-Fidelity Metrics (Direct Physical Correspondence)
These metrics are modeled with high accuracy, representing direct counterparts to physical hardware behavior:

1. **Relative Cache Miss Rates (L1D/L2)**
   * **Mechanism**: Simulated using gem5's cycle-accurate, timing-model cache blocks with standard Least Recently Used (LRU) replacement policy and non-blocking caches.
   * **Validity**: High. The relative differences in miss rates across cache capacities (32kB to 128kB L1D, 256kB to 1MB L2) reflect real-world working-set behavior under lock contention.
2. **Synchronization Overhead Patterns (Lock-Free vs. Lock-Based)**
   * **Mechanism**: Measured using compiler-generated atomic operations (`compare_exchange_weak`, `__sync_lock_test_and_set`) executed on simulated out-of-order execution pipelines.
   * **Validity**: High. The relative CPI and cycle overhead degradation of spinlocks (due to cache line bouncing and pipeline flushes) compared to CAS-based lock-free stacks is microarchitecturally realistic.
3. **Normalized Pipeline IPC (Instructions Per Cycle)**
   * **Mechanism**: Calculated by the CPU execution model using simulated hardware cycles and instruction decode/execute logs.
   * **Validity**: High. Identifies pipeline stall characteristics due to data dependencies and memory bus stalls.

### 1.2 Medium-Fidelity Metrics (Trend-Accurate / Proportional)
These metrics do not correspond directly to real-world absolute quantities but are highly representative of design trade-offs:

1. **Normalized Cycle and Tick Counts**
   * **Abstraction**: Because the workload task count was scaled down (from $N=1000$ to $N=100$) to enable tractable simulation times under cycle-accurate models, absolute cycle counts are lower than standard serving framework workloads.
   * **Validity**: Trend-Accurate. The relative speedup ratio ($Cycles_{lock\_free} / Cycles_{centralized}$) and the scalability slopes remain physically valid and scale predictably.
2. **Relative Execution Speedups**
   * **Abstraction**: The scheduling policies are simulated on a single node without complete Linux kernel network stack and driver overheads.
   * **Validity**: Proportional. The performance trends represent the pure algorithmic and microarchitectural bottlenecks without software stack masking.

### 1.3 Low-Fidelity/First-Order Metrics (Simplified Approximations)
These metrics are modeled using high-level analytical equations and should be used exclusively for trend visualization rather than absolute physical claims:

1. **PCIe Transfer Latency**
   * **Abstraction**: Modeled using the analytical formula $Latency = Size / Bandwidth$. It assumes ideal DMA channel allocation and does not capture PCIe transaction layer packet (TLP) header overhead, link training states, or physical host-to-device bus arbitration delay.
   * **Validity**: First-Order. Captures the primary scaling bottlenecks relative to model size and bandwidth sweeps, but ignores protocol-level jitter.
2. **CPU Orchestration and Tool-Call Latency**
   * **Abstraction**: Modeled as static latencies per request epoch.
   * **Validity**: Qualitative. Useful for demonstrating scheduling trade-offs, but does not capture dynamic CPU cache pollution caused by concurrent orchestrator context switching.

## 2. Statistical Interpretation Guidelines

To maintain scientific integrity for publication, the following rules must be observed when citing these data points in the manuscript:

1. **Never Report Absolute Timings as Physical Benchmarks**: 
   Do not state: "The system completes MoE inference in 1788.8 ms."
   Instead, state: "The Elastic-DCMD scheduling policy achieves a $20.2\times$ speedup over the baseline FCFS-Transfer scheme under high PCIe bandwidth constraints."
2. **Use Normalized Metrics for Cache and Memory Bus Analyses**: 
   When discussing memory performance, focus on *misses per kilo-instruction (MPKI)* or *relative cache hit improvement rates* rather than absolute miss counts.
3. **Explicitly Mention ISA and Platform Models**: 
   State clearly that the microarchitectural results are obtained via gem5 simulation modeling an ARMv8-A (or RISC-V RV64) out-of-order execution core running bare-metal static C++ binaries, to prevent confusion with full-stack Linux serving measurements.

## 3. Manuscript Documentation Reminders

* **Cite gem5 properly**: Ensure the specific gem5 version (23.0.0.1) and system emulation mode parameters are documented in the experimental setup section.
* **Acknowledge workload constraints**: Document that the task queue benchmarks utilize 100 requests with Zipf distribution characteristics to model representative MoE expert routing distributions.
