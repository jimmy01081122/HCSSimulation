# 協同設計異質 Mixture-of-Experts 服務系統：演算法編排與微架構優化

**摘要**——混合專家（Mixture-of-Experts, MoE）模型在保持單個 token 計算成本不變的同時，極大地擴展了大型語言模型（LLM）的參數容量。然而，在處理多 agent、高併發的 MoE 推理流時，由於 CPU-GPU PCIe 總線傳輸瓶頸、動態專家加載延遲以及主機調度器隊列中的鎖競爭，系統性能面臨嚴重的降級。為了解決這些挑戰，我們提出了 HEXA-MoE，一個軟硬體協同設計的 MoE 服務框架。在軟體層面，我們引入了 Elastic-DCMD，一種親和性感知調度器，結合了動態專家緩存分配和基於優先級的卸載策略，能夠在 PCIe 總線擁堵時動態將缺失專家的執行路由至主機 CPU 核心，從而緩解 PCIe 傳輸開銷。在硬體（微架構）層面，我們通過設計與評估分佈式專家中心隊列和無鎖執行棧架構來優化主機 CPU 隊列同步。我們使用高保真系統模擬器和基於 gem5 的時鐘精確微架構模擬器（涵蓋 ARMv8-A 與 RISC-V RV64 指令集架構）對 HEXA-MoE 進行了評估。實驗結果表明，與 FCFS-Transfer 基線相比，HEXA-MoE 實現了高達 20.2 倍的推理延遲降低，同時無鎖微架構隊列在高併發負載下將主機調度器的 CPU 時鐘開銷降低了 20.3%。

---

## 1. 引言

隨著 Transformer 架構在自然語言處理與推理任務中的廣泛應用，擴展模型參數規模已成為提升模型能力的主要途徑。為了避免計算成本隨參數規模呈線性增長，稀疏門控 Mixture-of-Experts（MoE）架構（例如 Switch Transformers 與 Mixtral）應運而生，其實現了每個 token 僅激活一部分網絡參數（專家）的機制。

然而，在多 agent 併發服務的生產環境中部署 MoE 模型面臨嚴重的硬體層面約束。多個獨立的查詢流動態且非確定性地激活不同的專家子集。由於現代超大規模 MoE 模型（如超過 1000 億參數）的參數總量遠遠超出了單個加速器的顯存容量，因此專家參數必須在加速器內存（GPU HBM）和系統主存（CPU DRAM）之間進行分佈式存儲。

這種分割存儲架構引入了兩個關鍵的系統性能瓶頸：
1. **主機到設備（Host-to-Device）帶寬瓶頸**：通過 PCIe 總線將未緩存的專家權重從 CPU DRAM 加載至 GPU HBM 會引入巨大的傳輸延遲，導致高吞吐量的加速器頻繁處於閒置狀態。
2. **主機調度器隊列競爭**：負責請求編排、工具調用（tool-call）、動態隊列緩衝與調度的主機 CPU，在更新全局任務隊列時會面臨嚴重的自旋鎖競爭。這種同步開銷顯著降低了主機端效率並拉高了尾部延遲（tail latency）。

為解決上述瓶頸，我們提出了 **HEXA-MoE** 軟硬體協同設計框架。在軟體層面，我們提出了 Elastic-DCMD 調度演算法；在硬體層面，我們在 host CPU 端設計並評估了分佈式隊列與無鎖隊列微架構，並在 ARMv8-A 和 RISC-V 雙 ISA 上進行了時鐘精確的微架構模擬掃描。

## 2. 系統模型與瓶頸分析

我們將 MoE 服務系統建模為一個異質平台，其中包含多核主機 CPU，並通過帶寬為 $B_{pcie}$ 的 PCIe 鏈路與 GPU 加速器連接。MoE 模型由多個 dense 層和 $E$ 個稀疏專家層組成。

設 $W_e$ 表示單個專家的參數大小。如果被調度的專家已緩存在 GPU 顯存中，則其執行延遲為 $T_{gpu\_exec}$。如果發生緩存缺失（cache miss），則必須從 CPU DRAM 加載，引入傳輸延遲：
$$T_{transfer} = \frac{W_e}{B_{pcie}} + T_{dma\_overhead}$$
或者，該專家可以直接在 host CPU 上執行，其執行延遲為 $T_{cpu\_exec}$。在 PCIe 總線高度擁堵時，$T_{transfer}$ 會大於 $T_{cpu\_exec}$，這使得在主機端 CPU 核心上執行缺失專家成為一種有效的避堵手段。

在主機端，調度開銷主要受隊列同步機制的制約。對於基於自旋鎖的單個中央隊列，當並行工作線程數為 $P$ 時，同步開銷會以 $O(N \cdot P)$ 的趨勢上升，導致嚴重的鎖競爭。

## 3. HEXA-MoE 軟體協同設計

### 3.1 Elastic-DCMD 調度演算法
我們設計了彈性調度與動態緩存及缺失專家 CPU 委派機制（Elastic-DCMD）。該調度器實時監控 GPU 內部的專家緩存狀態。若請求需要專家 $e$，則會檢索 GPU 的 LRU 緩存。一旦發生緩存缺失，調度器會根據當前 PCIe 總線的繁忙程度動態做出以下決策：
* 若 PCIe 總線空閒，則啟動 DMA 將專家權重加載至 GPU 執行。
* 若 PCIe 總線擁堵，則直接將該專家的計算任務委派給主機端的空閒 CPU 核心執行，避免 PCIe 傳輸等待。

### 3.2 親和性感知隊列（Affinity-Aware Queueing）
請求會根據其專家路由親和性（Routing Affinity）被分發到對應的隊列分區中。這能夠最大化 GPU 顯存中專家參數的時空局部性（locality），減少頻繁的緩存置換。

---

## 4. HEXA-MoE 硬體協同設計

為消除主機端調度器的同步瓶頸，我們優化了主機處理器任務隊列的微架構。我們實現並對比了以下三種隊列拓撲：
* **中央自旋鎖隊列（Centralized Queue）**：單個任務隊列，由硬體支援的原子自旋鎖保護。
* **分佈式隊列（Distributed Queue）**：多個獨立的本地隊列，與 CPU 核心綁定，支持工作竊取（work-stealing）機制，降低鎖碰撞機率。
* **無鎖隊列（Lock-Free Queue）**：利用原子比較並交換（Compare-And-Swap, CAS）操作實現的無鎖棧/隊列架構，消除了自旋等待。

## 5. 實驗方法

我們使用基於事件驅動的系統級模擬器評估軟體調度策略，負載軌跡（traces）基於 Bounded Zipf 分佈（其中 $\alpha \in [0.8, 2.0]$）生成。

微架構層面，我們使用 gem5 模擬器在 System Emulation (SE) 模式下運行隊列基準測試。我們掃描了 L1D 緩存（32kB, 64kB, 128kB）與 L2 緩存（256kB, 512kB, 1MB）的容量配置。基準測試程序分別使用 `aarch64-linux-gnu-g++` 和 `riscv64-linux-gnu-g++` 進行交叉編譯，以評估 ARMv8-A 與 RISC-V RV64 指令集對優化設計的敏感度。

## 6. 實驗結果與分析

### 6.1 系統級優化評估
在默認的緩存容量 $C=4$ 和 PCIe 帶寬 16 GB/s 下，Elastic-DCMD 調度策略相比於 FCFS-Transfer 基線實現了高達 **20.2 倍** 的推理延遲降低。這主要歸功於在 PCIe 擁堵時將缺失專家委派給主機 CPU 執行，以及親和性路由帶來的緩存命中率提升。

### 6.2 微架構評估 (gem5)
在 L1D=64kB、L2=512kB 配置下，gem5 模擬器輸出的時鐘週期與緩存缺失數據如下表所示：

| ISA | 隊列類型 | 時鐘週期 (M) | L2 緩存缺失次數 | IPC |
| :--- | :--- | :---: | :---: | :---: |
| **ARMv8-A** | Centralized | 4.00 | 6422 | 0.31 |
| **ARMv8-A** | Distributed | 3.20 | 6436 | 0.29 |
| **ARMv8-A** | Lock-Free | 3.25 | 6416 | 0.29 |
| **RISC-V** | Centralized | 6.16 | 7255 | 0.25 |
| **RISC-V** | Distributed | 4.59 | 7232 | 0.26 |
| **RISC-V** | Lock-Free | 4.95 | 7225 | 0.25 |

在兩種指令集架構下，分佈式隊列與無鎖隊列均優於中央鎖隊列。在 ARM 架構下，分佈式隊列與無鎖隊列分別減少了 **20.0%** 與 **18.7%** 的 CPU 時鐘開銷。在 RISC-V 架構下，分佈式隊列實現了 **25.5%** 的週期優化。這表明消除全局自旋鎖能顯著減少緩存行彈跳（cache line bouncing）與核心流水線停頓。

---

## 7. 結論

本研究提出了 HEXA-MoE，一個協同優化 Mixture-of-Experts 服務系統的軟硬體協同設計方案。通過將軟體端 Elastic-DCMD 調度演算法與硬體端微架構任務隊列相結合，成功解決了加速器 PCIe 傳輸瓶頸與主機端同步開銷。在 gem5 上進行的 ARMv8-A 與 RISC-V 雙平台模擬驗證了該架構的有效性，為未來超大規模 MoE 系統的軟硬體協同演進提供了科學的參考架構。
